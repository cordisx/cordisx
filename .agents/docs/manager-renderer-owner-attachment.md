# Manager renderer owner session foundation

This owner-side foundation does not attach a browser renderer or register its
plugins. Its only enabled channel is `plugin-management`, limited to the
existing management binding's `query` operation. Other management operations,
configuration, lifecycle, permissions, assets, and event streams are unavailable.

## Private RPC contract

The existing authenticated profile management RPC accepts
`operation.kind = 'manager-renderer'` with four actions. The manager sidecar
must construct these messages itself after it has authenticated an HTTP session:

- `open`: `{ gateway, browserSessionId }` returns `{ status: 'ok', handle, channels }`.
- `call`: `{ gateway, browserSessionId, handle, channel, payload }` returns
  `{ status: 'ok', value }`, `{ status: 'unavailable' }`, or `{ status: 'unknown' }`.
- `close`: `{ gateway, browserSessionId, handle }` closes an opened renderer.
- `revoke`: `{ gateway, browserSessionId }` also fences an `open` that has not
  completed. Call this when the HTTP session is retired, even if its open is
  still in flight. On any race the sidecar must also close a returned handle if
  the corresponding HTTP session has already been retired.

`gateway` is the manager's own `{ pid, processStartedAt, instanceToken }`.
`browserSessionId` is the sidecar's private session ID, generated by the
sidecar. `handle` contains `{ rendererId, ownerGeneration, grant }`. Never take
any of these fields from the browser, place them in browser bootstrap data, or
log them. The sidecar must associate the handle with its authenticated session
and send binding requests using that association. `open` results are private
to the owner-to-sidecar RPC and are not browser responses. The sandbox mailbox
must continue to reject the `manager-renderer` operation.

The sidecar now connects authenticated HTTP sessions to this owner RPC. It
derives the gateway, session ID and handle internally, accepts only the channel
explicitly advertised by the owner, and revokes on session retirement. The
browser binding transport and a full production renderer composition are still
separate work; this HTTP route alone does not mount the Manager or its plugins.

For the one read-only channel, `payload` is the original JSON string from
`__cordisxPluginManagementRequestV1`. The owner checks its profile and existing
request parser, accepts only an exact `{ kind: 'query' }` operation, then calls
the owner's `PluginManagementService`. The renderer-supplied binding token is
not the authorization; the owner substitutes a parser-only sentinel after the
sidecar session has been authenticated. The result is the existing binding
response `{ requestId, ok: true, value }` nested inside the RPC result. The
sidecar should deliver it through `__cordisxPluginManagementReceiveV1` only to
the originating browser session; map unavailable/unknown to a bounded error,
and never retry an unknown write automatically.

When the owner composition closes it disposes the authority before closing the
RPC and service; in-flight reads are fenced and dispatched writes become
unknown. Manager liveness is checked periodically and on each admitted call.
Session lifetime is at most eight hours, with at most 16 live sessions and
4,096 previously used session IDs per owner generation. Exhaustion fails
closed and needs an explicit renewal design before relying on long-lived
high-churn owners.

Authentication follows the existing local manager trust boundary: the record
and Unix control socket are private to the OS user, but Node's current socket
API does not attest the caller's PID. It does not protect against another
malicious process under that same OS identity. The browser is not treated as
an owner child process. No integration here claims an attached real Desktop,
federated plugin graph, snapshot notifications, or lifecycle mutation.

## Browser resource transport (not yet wired to the Manager)

`createManagerResourceAuthClient` binds the in-memory browser session bearer to
the fixed `/manager-resource-worker.js` for the calling top-level document.
The worker attaches that bearer only to same-origin GET requests for the exact
`/api/renderer/bundle.js` path and bounded `/api/renderer/graphs/<id>/<file>`
paths. It derives the requester from `FetchEvent.clientId`; it does not grant
access to any graph. The HTTP server must authenticate the bearer, choose the
matching `SessionPluginGraphProjection`, and validate every lease and request.
The bearer must never be included in URLs, diagnostics, or persistent storage.

The public entry must register the fixed worker, wait for its session binding,
then import the authenticated bundle. Serve the worker as same-origin JavaScript
and allow `worker-src 'self'` and `font-src 'self'` in the standalone document's
CSP. Other existing CSP restrictions remain in force. Worker registration is
limited to the manager origin; a newer worker waits for old clients to close
instead of replacing an active controller during a lifecycle transaction.
The client verifies the controlling worker's exact script URL before sending a
bearer. Existing inline Host or plugin style elements are not made CSP-compatible
by this transport and require their own trusted style-delivery solution.

A worker restart erases its in-memory bindings, so resource requests fail closed.
The document may call `recover()` only after checking the server-side session;
the resource caller decides whether a safe reload is needed. `revokeLocal()`
erases the local token and aborts in-flight reads, but cannot revoke the server
session or erase code already imported. Closing or replacing an owner must also
revoke the HTTP session and its graph leases. This is a resource gateway, not a
sandbox for mutually hostile same-origin scripts or windows.

The standalone renderer bundle can exceed the existing 8 MiB owner management
RPC response limit (an empty-plugin measurement was approximately 36.8 MB).
Serving the protected bundle therefore also needs an owner-controlled bounded
artifact or streaming transport; returning the whole bundle as a single
management RPC response is not a valid integration.

The isolated browser test composes the actual artifact server and session graph
projection, then checks nested ESM, CSS, image and font requests, cross-tab and
direct bypass denial, restart/recovery, local in-flight revocation, and server
revocation. It does not exercise the product Manager entry, real plugin
lifecycle federation, or a native Desktop renderer.
